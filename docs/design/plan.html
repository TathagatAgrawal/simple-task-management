Design plan · v2 · 14 Nov 2026

A one-page task board for a three-person CA firm

The smallest useful thing: a shared board of tasks, each with one or more owners, a due date, an optional repeat schedule and a running thread of updates. Everyone sees what's on their plate and what's due in the next three days. One admin can add or remove people. It runs on a Windows 10 PC in the office and staff open it privately over Tailscale from their desktop browsers.

What changed since v1

  • Host is a Windows 10 PC. Setup, the always-on service, power settings and backups are now Windows-specific (§9, §10).
  • Everyone shares one Tailscale login, so Tailscale can't tell people apart. App passwords stay, and the "sign in via Tailscale identity" idea is dropped.
  • Timezone fixed to IST (Asia/Kolkata).
  • Recurring tasks are in v1: weekly, monthly, quarterly or yearly, with a new section explaining how they work (§6).
  • Desktop-first. Phone layouts are out of scope for now, and cards move between columns by drag-and-drop.
  • Multiple assignees per task via a task_assignees join table.
  • Light and dark themes with a per-person switch (System / Light / Dark) that follows them to any computer. Use the switch at the top of this page to view the whole doc in either theme.

1. Goals and non-goals

What it must do

  • Tasks have a title, optional notes, one or more assignees, a due date and a status: To do, Doing or Done.
  • Recurring tasks repeat weekly, monthly, quarterly or yearly. When one is marked done, the next occurrence appears on the board automatically with the same assignees.
  • Updates thread on every task. Anyone can post a comment or progress note. Changes to status, assignees, due date and repeat schedule are logged in the same thread automatically, so the thread is the full history.
  • My tasks view. Each person can filter the board to tasks they're assigned to, and this is the default when they open the app.
  • "Coming up" summary across the top: Overdue, Due today and Next 3 days. Overdue isn't strictly in the brief, but a missed deadline that falls off the summary is the most likely way a task gets lost, so it's included.
  • Drag-and-drop cards between columns to change status.
  • One page. The board, the task details, the dialogs and the login screen are all states of the same page. Nothing navigates away.
  • Light and dark themes. Each person picks System, Light or Dark, and the choice is saved to their account.
  • Simple admin. One flag, is_admin. Admins can add people, remove (deactivate) people and reset passwords. Everyone else can do everything else.
  • Runnable by non-technical people. Staff only ever open a bookmark. Setup is done once on the Windows host by whoever is most technical, and after that the app needs no maintenance.

What it deliberately won't do (v1)

  • No mobile layout. The target is a desktop browser at 1280px or wider. The page will still work on a 1024px laptop, but phones aren't designed for or tested. A phone layout comes in a later version (§14), and the design leaves room for it.
  • No roles or permissions beyond admin and not-admin. Anyone can edit any task, which is fine for three people who trust each other.
  • No projects, labels, priorities, sub-tasks, time tracking, file attachments or email notifications.
  • No manual ordering of cards within a column. Each column is always sorted by due date, which is the order that matters for deadlines. Drag-and-drop only moves cards between columns.
  • No public internet exposure. The app is only reachable from devices on the firm's tailnet (§10).

2. Key decisions at a glance

Language
Python 3.13
Already set up in this repo with uv. uv also installs Python on the Windows host.
Web framework
FastAPI + Jinja2
Server-rendered HTML. No build step, no Node.
Interactivity

htmx swaps parts of the page in place. Native HTML5 drag-and-drop needs no library.
Database
SQLite (WAL mode)
One file, nothing to install or administer, and easy to back up.
Auth
Username + password, 30-day cookie
Required, because the shared Tailscale login can't identify people.
Network access
Tailscale Serve
Private HTTPS URL on the tailnet. No port forwarding and no firewall rules.
Host
Windows 10 PC
Runs at boot via Task Scheduler, with Tailscale in "Run unattended" mode.
Theme
System / Light / Dark
CSS variables. The choice is stored on the user, so it follows them between computers.

Why not Postgres, React, Docker, etc.? At three users and a few thousand tasks a year, each of those adds a moving part that someone has to keep running without adding anything the firm would notice. Docker on Windows 10 in particular means WSL2 and Docker Desktop, which is a lot of machinery for one small app. The whole app should be about 800 lines of Python plus templates, and a single uv run command should start it.

How the "one page" works

The browser loads / once. After that, every click or drop sends a small htmx request and gets back an HTML fragment that replaces one region of the page: the board, the "coming up" strip, the task panel or a dialog. The server owns all state and rendering, so there's no client-side data model to keep in sync.

When a task changes, the server sends an HX-Trigger: tasks-changed response header. The board and summary listen for it and reload themselves, so all regions stay consistent.

Drag-and-drop

Drag-and-drop uses the browser's native HTML5 API, which works well on desktop and needs no library. Cards get draggable="true" and data-task-id, and each column has data-status. On drop, about 60 lines in static/board.js call htmx.ajax("POST", "/tasks/42/move", {values: {status: "doing"}}). The server writes the change and the history entry and returns the refreshed board. Dropping a card in its own column does nothing. Moving a recurring task to Done by dragging creates the next occurrence, the same as clicking the Done button (§6).

Seeing each other's changes

The board polls quietly every 60 seconds (hx-trigger="every 60s, tasks-changed from:body") and also refreshes when the browser tab regains focus. Polling pauses while a drag is in progress so a refresh can't pull the card out from under the cursor.

Five tables. A task with no rows in task_assignees shows as "Unassigned". Comments and automatic change entries share the updates table, separated by kind, so the thread is one ordered query.

Notes on the model

  • Dates: due_date is a plain date with no time. Timestamps are stored as UTC ISO strings and shown in IST. "Today" is always calculated in Asia/Kolkata through Python's zoneinfo, so it doesn't depend on the Windows clock's timezone setting. Windows has no built-in timezone database, so the tzdata package is added as a dependency.
  • Multiple assignees: the composite primary key (task_id, user_id) prevents duplicates. Adding or removing an assignee writes an event to the thread, for example "Asha added Meera".
  • Removing people is a soft delete (is_active = 0). Their name stays on old comments, they can no longer sign in, and their sessions are deleted. Their rows are removed from open tasks' assignees, with an event on each thread, so tasks shared with someone else just lose one avatar.
  • Tasks are never hard-deleted in normal use. A "Delete" action in the panel exists to clean up mistakes and asks for confirmation.
  • Indexes: tasks(status, due_date), task_assignees(user_id), updates(task_id, created_at) and a unique index on tasks(prev_task_id). The last one guarantees a recurring task can never spawn two next occurrences.

The "coming up" query

-- :today is computed in IST; :who is a user id, or NULL for everyone
SELECT DISTINCT t.*
FROM tasks t
LEFT JOIN task_assignees a ON a.task_id = t.id
WHERE t.status != 'done'
  AND (:who IS NULL OR a.user_id = :who)
  AND t.due_date <= date(:today, '+3 days')
ORDER BY t.due_date;
-- Python then buckets rows into: overdue (< today), today (= today), next 3 days (> today)

6. Recurring tasks

CA work is full of fixed-rhythm deadlines: GST returns every month, TDS every quarter, ITR and audit every year. Recurring tasks keep these on the board without anyone retyping them.

How it works

  • Choices: Never, Weekly, Monthly, Quarterly (every 3 months) or Yearly. These are set from the "Repeats" dropdown in the new-task dialog or the task panel.
  • Each occurrence is its own task. The thread for October's GSTR-3B stays with October's task. All occurrences share a series_id, so a "previous occurrences" link in the panel can list them.
  • The next occurrence is created when the current one is marked Done, by drag or button. It copies the title, notes, assignees and repeat setting, starts in To do, and both threads get a linking event: "Next occurrence created, due 20 Dec" on the old one and "Continued from the 20 Nov task" on the new one.
  • The next due date is calculated from the previous due date, not the completion date, so the schedule never drifts. Filing November's GSTR-3B late on 25 Nov still makes December's due on 20 Dec.
  • Month-end handling: repeat_day remembers the original day of the month. A task anchored on the 31st goes 31 Jan → 28 Feb → 31 Mar, not 31 Jan → 28 Feb → 28 Mar.
  • Reopening and re-closing a task doesn't create a duplicate, because the unique index on prev_task_id blocks it.
  • Stop repeating: set Repeats to Never on the current occurrence, and no next one will be created.
  • Irregular deadlines: some statutory dates aren't evenly spaced. For example, the Q4 TDS return is due 31 May instead of 30 April. For these, the person adjusts the date on the new occurrence, which is logged in the thread like any change. A "custom date list" schedule could be added later if this gets tedious.

All of this runs in the same database transaction as the status change, so a crash can't leave a done task without its successor.

Why create the next one on completion rather than on a calendar? It's simpler (no scheduler), and it never produces a pile of identical overdue copies if someone falls behind. The cost is that next month's task isn't visible until this month's is done. For a firm working one period at a time that's usually what people want. The overdue one stays red at the top of the summary until it's dealt with.

9. Login, admin and themes

Login

Because everyone shares one Tailscale login, Tailscale can only prove that a request comes from a firm device, not which person sent it. The app needs its own sign-in so that comments, assignments and history show the right name.

  • First run: uv run simple-task-management create-admin prompts for the first admin's name, username and password. It's the only command-line step anyone needs after install.
  • Adding people: the admin enters a name and username in the People dialog and gets a temporary password to read out or WhatsApp to the person. On first sign-in, that person sets their own password.
  • Forgotten password: the admin clicks "Reset password". There's no email flow.
  • Shared office computer? "Sign out" is in the user menu. Sessions last 30 days per browser, so on a computer used by more than one person, each person should use their own Windows account or browser profile.
  • Safety rails: there must always be at least one active admin, and an admin can't remove themselves.
  • Password storage: hashlib.scrypt (n=214, r=8, p=1) with a per-user random salt, stored as scrypt$n$r$p$salt$hash. It's in the standard library, so nothing extra to install.
  • Brute force: the app is only reachable from the tailnet, but it still applies a small per-username delay after 5 failed attempts.

Themes

  • Three settings: System (follows the Windows light/dark setting, and is the default), Light and Dark. The control is in the user menu, as shown in the mockups.
  • Stored on the user (users.theme), not in the browser, so a person sees their choice on any computer they sign in from.
  • No flash on load: the server renders <html data-theme="dark"> (or no attribute for System) directly into the page, so the right colours appear from the first paint. Changing the setting flips the attribute immediately in JS and saves it with POST /me/theme.
  • CSS: one set of variables (--bg, --surface, --text, --muted, --border, --accent, and status colours with their soft backgrounds). Light values sit on :root. Dark values are defined twice: under @media (prefers-color-scheme: dark) for System, guarded by :root:not([data-theme="light"]), and under :root[data-theme="dark"] for an explicit choice. The login screen follows System, since there's no user yet.
  • Contrast: both palettes are checked against WCAG AA (4.5:1 for text) before shipping, especially the red, amber and blue chip text on their soft backgrounds.

Windows 10 security updates. Microsoft ended Windows 10 support in October 2025, and the consumer Extended Security Updates programme ran only to October 2026. Unless the firm has paid business ESU, this PC no longer gets security patches. The app limits exposure (it listens only on localhost and is reachable only over the tailnet), but the PC itself still browses the web and opens email. Recommendations: use it only as the server, keep Defender and Tailscale updated, and plan a move to Windows 11 or a small Linux box when convenient. Moving the app later is just copying one folder.

One-time setup on the Windows host (done once by the most technical person)

The repo will ship deploy\windows\install.ps1, which runs steps 3–6. They're spelled out here so it's clear what it does.

# 1. Tailscale (already installed) — make sure it keeps running when nobody is logged in:
#    Tailscale tray icon → Preferences → "Run unattended" ✓
#    Tailscale admin console → Machines → rename this PC to "tasks"
#    Admin console → DNS → MagicDNS ✓ and HTTPS Certificates ✓
#    Admin console → Machines → tasks → "Disable key expiry" (so the server never silently drops off)

# 2. Power: Settings → System → Power & sleep → Sleep: Never (on AC)
#    Windows Update → Active hours: e.g. 8 am – 10 pm (reboots happen outside office time)

# 3. Install uv (also installs Python 3.13 for the app) — in a normal PowerShell:
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 4. Put the app in C:\TaskBoard (git clone, or unzip a release) and install dependencies
cd C:\TaskBoard
uv sync

# 5. Create the first admin
uv run simple-task-management create-admin

# 6. Register the app to start at boot and restart if it crashes (Task Scheduler)
#    (install.ps1 does this — shown for clarity)
$uv       = "$env:USERPROFILE\.local\bin\uv.exe"
$action   = New-ScheduledTaskAction -Execute $uv `
              -Argument "run simple-task-management serve --host 127.0.0.1 --port 8000" `
              -WorkingDirectory "C:\TaskBoard"
$trigger  = New-ScheduledTaskTrigger -AtStartup
$settings = New-ScheduledTaskSettingsSet -RestartCount 999 -RestartInterval (New-TimeSpan -Minutes 1) `
              -ExecutionTimeLimit (New-TimeSpan -Seconds 0) -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries
Register-ScheduledTask -TaskName "TaskBoard" -Action $action -Trigger $trigger -Settings $settings `
  -User $env:USERNAME -Password (Read-Host "Windows password for $env:USERNAME") -RunLevel Limited
Start-ScheduledTask -TaskName "TaskBoard"

# 7. Publish it to the tailnet with HTTPS — in an *Administrator* PowerShell (persists across reboots)
tailscale serve --bg 8000
tailscale serve status        # shows https://tasks.<your-tailnet>.ts.net

Why Task Scheduler and not a third-party service wrapper (NSSM, WinSW)? It's built into Windows, needs nothing downloaded, can restart the app on crash, and with "run whether user is logged on or not" (which is what passing -Password sets up) it starts at boot before anyone signs in to the PC.

What each staff member does

  1. Make sure Tailscale is running on their desktop. It already is.
  2. Open https://tasks.<your-tailnet>.ts.net and bookmark it. Optionally pin it as an app with Chrome or Edge → ⋮ → "Install page as app", so it opens in its own window from the taskbar.
  3. Sign in with the username and temporary password from the admin, then set your own password.

Don't use Tailscale Funnel (the feature that makes a tailnet service public on the internet). Task titles will contain client names and compliance details. Keeping the app tailnet-only means an attacker would need a device on the firm's tailnet before they could even reach the login page.

With a shared Tailscale account, the account itself is the front door. Anyone who signs into it on any device joins the tailnet. Turn on two-factor authentication for that account, enable Device approval in the Tailscale admin console so new devices must be approved, and remove old devices from the Machines list. Per-person access rules (ACLs) aren't possible with one shared identity, which is another reason the app keeps its own passwords.

11. Backups, updates, and keeping it running

  • Folders: the app lives in C:\TaskBoard and the live database in C:\TaskBoard\data\tasks.db. Keep the live database outside OneDrive or Google Drive, because sync tools can corrupt an open SQLite file.
  • Nightly backup, built in. A background task in the app runs at 23:00 IST. It uses sqlite3.Connection.backup(), which is safe while the app is running, to write tasks-YYYY-MM-DD.db into BACKUP_DIR, and keeps the last 30. Point BACKUP_DIR at a OneDrive or Google Drive synced folder, for example C:\Users\Office\OneDrive\TaskBoard-backups, so there's an off-machine copy with no extra work. A backup is also taken before every update.
  • Restore: run restart.ps1 -Stop, copy a backup over data\tasks.db, then run restart.ps1. This is written up in the README.
  • Updating the app: run update.ps1. Schema migrations run automatically at startup, gated by PRAGMA user_version.
  • Is it up? status.ps1 on the host, or /healthz from any browser. Failures are logged to C:\TaskBoard\logs\app.log, rotated daily and kept for 14 days.
  • After a power cut: if the PC's BIOS has an "AC power recovery: On" option, turn it on so the PC boots by itself. Task Scheduler and Tailscale (unattended) then bring everything back with no one at the keyboard.
  • Config via a .env file in C:\TaskBoard: DATA_DIR, BACKUP_DIR, LOG_DIR, TIMEZONE=Asia/Kolkata, BACKUP_HOUR, BACKUP_KEEP. No secret key is needed: sessions are random tokens stored in the database, and each session carries its own CSRF token.

Testing approach

  • pytest with FastAPI's TestClient against a temp SQLite file per test.
  • dates.py and recurrence.py are pure functions that take today or due as parameters. They're tested over a table of cases: 31 Jan monthly, 29 Feb yearly, quarterly across a year boundary, weekly across a month boundary.
  • Assignee tests: "My tasks" and the summary include tasks shared with others, removing a person leaves co-assignees intact, and a task with zero assignees shows as Unassigned.
  • Permission tests: non-admins get 403 on /people*, removed users can't sign in, and the last admin can't be removed.
  • A manual check from a second PC over Tailscale, in both themes, before handing it over. A reboot test on the host with nobody signed in.

14. Later versions

  • Mobile layout (planned next). Below about 700px, the columns become tabs, the "coming up" strip becomes count chips, and the task panel goes full-screen. Drag-and-drop is replaced by status buttons on touch devices. The phones would need the Tailscale app signed into the shared account. The server-rendered fragments don't change; this is mostly CSS plus a touch check in board.js.
  • Client field: an optional "client" on a task, with a client filter in the top bar.
  • Custom recurrence dates for irregular statutory calendars (e.g. TDS: 31 Jul, 31 Oct, 31 Jan, 31 May).
  • Morning digest: a daily email or WhatsApp message to each person with their "coming up" list.
  • Attachments: files stored on disk next to the database and linked from updates.
  • Search across titles and updates using SQLite FTS5.
