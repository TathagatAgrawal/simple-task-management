Web Push, and telling the person who created a task

One pull request with two changes. First, fix a gap in the notifications we already have: the person who created a task is told nothing when someone else works on it. Second, add Web Push, so alerts reach a phone's lock screen and a desktop even when the board is closed. This is the design record. It has been built; where it differs from the code, the code wins.

The short answer. A push is sent for exactly the same events that already put a line in the bell, to the same people, and only to people who have "Pop up and bell" turned on for that kind of change. Nothing new is announced; the only new thing is that the alert can now reach a closed app. The creator fix adds one more person to that list: whoever created the task.

1. Change one: the creator hears about their task

What happens today

Asha creates a task and assigns it to Ravi alone. Ravi marks it Done, or posts an update. Asha gets nothing. The reason is in store._notify: unless a caller passes a list, it tells the task's current assignees, minus whoever made the change. Asha made the task but is not an assignee, so she is on nobody's list.

The fix

The default recipients become the task's assignees plus the person who created it, still minus whoever made the change, with duplicates removed. It is one rule in one place, so every kind of change gets it: edits, moves, comments, assignee changes, deletion. Each person's own settings still apply, so Asha can turn comments down to "Bell only" or "Nothing" like anyone else.

Details worth knowing

  • No double alerts. If the creator is also an assignee they get one notification, not two.
  • Only active people. A creator who has been removed from the firm, or a task with no recorded creator, is skipped, as for any recipient today.
  • "You were assigned" and "you were removed" stay as they are. Those two go only to the person added or removed. The creator instead hears the summary line ("added Meena · removed Ravi") through the ordinary "changed" notification.
  • Recurring tasks. The next occurrence copies its creator, so the person who set up a quarterly return keeps hearing about every quarter's copy.
  • Existing tasks. No backfill. Creators start hearing about changes made after the update. Their existing bell is not rewritten.
  • The old test stays true. "A new task tells the assignees but not the creator" still holds, because the creator is the person who made the change.

2. Change two: when and what a push sends

The rule

Every time a notification is written for someone with the setting Pop up and bell for that kind, a push is sent to every phone or computer where that person has turned phone and desktop alerts on. People set to Bell only or Nothing for a kind get no push for it. The person who made the change never gets one. There are no other triggers: no daily digest, no overdue reminder, no marketing.

What is not sent

  • Anything for a kind you set to "Bell only" or "Nothing".
  • Anything for a change you made yourself.
  • A reminder that a task is due or overdue. Those need a scheduler and a decision about timing, so they are out of this pull request. The bell and the overdue strip still show them when the board is open.
  • A push for a task that was already a notification before the update. The first release marks every existing notification as already handled, so nobody is flooded.

3. How it works

  1. Turning it on. A person opens the bell's settings and presses Turn on alerts on this device. The browser asks permission and hands the app a private address for that device. The app saves it against that person. Each device has its own, so a phone and a laptop can both be on.
  2. A change is made. The existing transaction writes the task change, the history line and the notification rows together, exactly as now. Nothing about that changes, so a push problem can never lose or block a task change.
  3. Sending. Once the change is saved, a small background task in the app finds notification rows that should alert and have not been pushed yet, encrypts a short message for each of that person's devices, and posts it to Apple, Google or Mozilla's push service. That service wakes the device. The row is then marked pushed, so a restart never sends it twice.
  4. Showing it. The device wakes the service worker (sw.js), which shows the banner. Tapping it opens the task.
  5. Cleaning up. If a push service says the device is gone (it answers 404 or 410), the subscription is deleted. Signing out removes that device's subscription. Pressing Turn off does too.

One place for alerts: the system

  • Turned on for this device (permission granted and a subscription saved): the board never shows its own popup. The bell number and list update live. Alerts come from the system: the iPhone banner, the Windows toast, the macOS notification.
  • Not turned on (never enabled, blocked, or a browser that cannot do push): the board keeps showing its on-page message, and the desktop alert while the tab is hidden, exactly as today. Nobody loses alerts.
  • Stays on screen until dismissed: assignments, removals, deletions and due-date changes (the same notifications the server already marks sticky) use requireInteraction on desktop. Others fade on their own. iOS ignores this and uses its normal banner.
  • Icon badge: each push carries the person's unread count, and the service worker sets it on the Home Screen or installed-app icon with the Badging API (iOS 16.4 and newer, installed desktop apps). It is a bonus: if a platform ignores it, nothing else changes. Untested on iOS until tried on a phone.
  • Menu wording: "Pop up and bell" is renamed "Alert and bell", because on these devices the alert is the system's, not a pop-up in the board.

5. Checks and tests

  • Creator rule. One test per row of the table in section 1, including the duplicate, inactive and no-creator cases, and a test that the creator's "Nothing" setting is honoured.
  • Push rules. With the sender replaced by a recording fake: a push goes out only for rows set to alert, never to the actor, to every device of a person, and never twice for one row. A 410 reply removes the subscription. A sender that raises does not stop the loop, the task change, or other people's pushes.
  • Migration. A version 5 database upgrades with its notifications marked pushed and no stray pushes at startup, and the migration is atomic like the others.
  • API. Subscribe, replace, unsubscribe, and that one person cannot read or remove another's subscription.
  • Client. The settings control in each state (can turn on, on, blocked by the browser, unsupported), and the push handler's skip-when-visible rule.
  • Whole flow in a browser. I can check the button, subscription and handler on a Mac. I cannot receive a real push on an iPhone from here. After the PR is up, you would try it on your phone over Tailscale with the demo data, and I would give you the exact steps. Delivery to Apple is the one part that stays unproven until then.

6. Risks

  • Apple is strict. iOS needs every push to show something, and drops a subscription that sends silent ones. So the service worker always shows the banner, on every device, whether or not the board is open. Because the board shows no popup of its own on those devices, nobody sees two alerts. Untested: whether iOS draws the banner while the Home Screen app is in front. Either way there is one alert, and the bell number updates.
  • Slower than before. A push travels through Apple, Google or Mozilla, so it takes a second or a few. The bell number still updates instantly over the live connection.
  • Lock screens are visible. Task titles can name clients. That is the reason section 7 asks about banner text.
  • One more thing that can break on the PC. A failed push never affects the board, and the in-app bell and on-page alerts keep working. The only symptom would be "my phone stopped buzzing". Failures are written to the app's log, and the plan adds a line to operations.md on where to look.
