Notify people when a task is assigned to them

An inbox inside the app, plus an operating-system notification, so Meera hears about a new task without watching the board. This page shows how it would work in the backend and in the frontend, and what it would cost in dependencies.

Status: built on branch feat/notifications (Phases 1 and 2). Differences from this proposal. Every change to a task now notifies its other assignees (not only assignment), and the notification stores its text (so it survives a deleted task). A toast shows on the page whenever it is visible, even when focused, because the bell is easy to miss; the OS alert is used when the window isn't focused. On a phone, the Alerts tab replaces the bell. Each person can also choose, per kind of change, "Pop up and bell", "Bell only" or "Nothing" (Notification settings in their menu); the default is "Pop up and bell" for everything. Phase 3 (Web Push) is not built. Since this page was written the app moved to a TypeScript client on the JSON API with live updates over Server-Sent Events, so the bell is refreshed by a push from the server (with a 60-second safety net) instead of the polling and HTMX fragments described below.

Can it be done? Yes. Two parts need nothing new to install, and a third part is optional.

  1. Notifications section in the app. A bell in the top bar with an unread count, and a list where each notification can be marked read or unread, dismissed (removed), or cleared in bulk. One new table, plain SQL in store.py, the same HTMX fragment pattern as the rest of the app. No new dependency.
  2. An OS notification while the app is open. The page asks the operating system to show a native notification (Windows Action Center, macOS Notification Centre, Android shade) through a tiny service worker. It looks like any other app's notification, not like a page popup. No new Python dependency. It only fires while the board is open in some browser tab or installed window, within about a minute of the assignment.
  3. An OS notification even when the browser is closed (Web Push). Possible, but it adds a Python dependency, signing keys, a subscriptions table and a reliance on the browser vendors' push services. Recommended only if staff turn out to close the board.
One thing cannot be removed: the permission prompt. Every browser asks once, per person and per browser, "Allow notifications?". It is a security rule of the browser, not something the app can skip. The proposal keeps it to one deliberate click on a button inside the app ("Turn on desktop alerts"), so nobody gets a surprise prompt on page load, and the notifications themselves appear as OS notifications, not as in-page popups.

3. Backend

3.1 One new table

Notifications are a convenience, not history. The permanent record stays in the task's thread (the event row that already says "added Meera"), so deleting a notification never loses anything. That is why a dismissed notification is really deleted.

src/simple_task_management/db.py — MIGRATIONS[0] (and mirrored in schema.sql) 
CREATE TABLE notifications (
    id         INTEGER PRIMARY KEY,
    user_id    INTEGER NOT NULL REFERENCES users (id),          -- who is told
    task_id    INTEGER NOT NULL REFERENCES tasks (id) ON DELETE CASCADE,
    actor_id   INTEGER REFERENCES users (id),                   -- who did it
    kind       TEXT    NOT NULL DEFAULT 'assigned' CHECK (kind IN ('assigned')),
    created_at TEXT    NOT NULL,
    read_at    TEXT                                             -- NULL = unread
);

CREATE INDEX notifications_user ON notifications (user_id, read_at, id);
  • The text is not stored. It is built when shown, from a join on the task and the actor, so a renamed task or a changed due date is always current.
  • ON DELETE CASCADE: deleting a task removes its notifications.
  • People are never hard-deleted (is_active = 0), so user_id and actor_id always resolve.
  • Retention without a background job: every time a notification is written, delete this table's rows that were read more than 30 days ago, in the same transaction.

3.2 Writing a notification, inside the existing transaction

The rule lives in store.py next to the code that already logs the event, so it cannot be skipped by any route or by the JSON API. This follows the project rule that a task change and its side effects commit together.

src/simple_task_management/store.py 
def _notify_assigned(
    conn: sqlite3.Connection, actor: sqlite3.Row, task_id: int, user_ids: list[int], now: str
) -> None:
    """Tell each newly assigned person about the task, except the person who assigned it."""
    rows = [(uid, task_id, actor["id"], now) for uid in user_ids if uid != actor["id"]]
    conn.executemany(
        "INSERT INTO notifications (user_id, task_id, actor_id, created_at) VALUES (?, ?, ?, ?)",
        rows,
    )
    cutoff = (datetime.fromisoformat(now) - timedelta(days=30)).isoformat(timespec="seconds")
    conn.execute("DELETE FROM notifications WHERE read_at IS NOT NULL AND read_at < ?", (cutoff,))

Two one-line calls, each inside the with conn: block that already exists:

# create_task(), after the assignees are inserted

    _notify_assigned(conn, actor, task_id, ids, now)

3.3 Reading and changing notifications

Every function takes the signed-in person's id and filters on it, so nobody can read or change someone else's notifications by guessing an id.

src/simple_task_management/store.py 
def notifications_for(conn: sqlite3.Connection, user_id: int, limit: int = 50) -> list[sqlite3.Row]:
    """My notifications, newest first, joined to the task and the person who assigned it."""
    return conn.execute(
        """SELECT n.id, n.created_at, n.read_at, n.task_id, t.title, t.due_date, t.status,
                  a.name AS actor_name
           FROM notifications n
           JOIN tasks t ON t.id = n.task_id
           LEFT JOIN users a ON a.id = n.actor_id
           WHERE n.user_id = ? ORDER BY n.id DESC LIMIT ?""",
        (user_id, limit),
    ).fetchall()


def unread_summary(conn: sqlite3.Connection, user_id: int) -> tuple[int, int]:
    """Return (unread count, newest notification id) for the bell badge."""
    row = conn.execute(
        "SELECT COUNT(*) FILTER (WHERE read_at IS NULL), COALESCE(MAX(id), 0) "
        "FROM notifications WHERE user_id = ?",
        (user_id,),
    ).fetchone()
    return row[0], row[1]


def set_notification_read(
    conn: sqlite3.Connection, user_id: int, notification_id: int | None, *, read: bool
) -> None:
    """Mark one notification (or all of mine, when the id is None) read or unread."""
    stamp = now_iso() if read else None
    where, args = ("user_id = ?", [user_id])
    if notification_id is not None:
        where, args = (where + " AND id = ?", args + [notification_id])
    with conn:
        conn.execute(f"UPDATE notifications SET read_at = ? WHERE {where}", [stamp, *args])


def dismiss_notifications(
    conn: sqlite3.Connection, user_id: int, notification_id: int | None, *, only_read: bool = False
) -> None:
    """Delete one of my notifications, or every read one when the id is None."""
    where, args = ("user_id = ?", [user_id])
    if notification_id is not None:
        where, args = (where + " AND id = ?", args + [notification_id])
    if only_read:
        where += " AND read_at IS NOT NULL"
    with conn:
        conn.execute(f"DELETE FROM notifications WHERE {where}", args)

Marking read does not log an event on any task: it changes a private inbox, not the task, so the "every task change writes an event" rule does not apply.

4.4 The OS notification (Phase 2)

A new route serves a service worker at /sw.js (from a route, not /static/, so its scope is the whole site, the same way /manifest.webmanifest is served). It has two jobs: show the notification, and focus or open the app when it is clicked. No caching, so there is no offline mode to maintain.

src/simple_task_management/static/sw.js (about 15 lines) 
/* Shows OS notifications for the task board and opens the task when one is clicked. */
self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const url = event.notification.data.url;
  event.waitUntil(
    clients.matchAll({ type: "window", includeUncontrolled: true }).then((wins) => {
      const open = wins.find((w) => new URL(w.url).origin === location.origin);
      return open ? open.navigate(url).then((w) => w.focus()) : clients.openWindow(url);
    })
  );
});

The page decides when to alert. It remembers, per browser, the newest notification id it has already alerted for, so nothing fires twice and old unread items never fire after a fresh sign-in.

src/simple_task_management/static/board.js — new section 
// Desktop alerts: after each badge refresh, alert for anything newer than the last id we alerted for.
document.body.addEventListener("htmx:afterSwap", async (e) => {
  if (e.target.id !== "bell-badge" && e.detail.target?.id !== "bell-badge") return;
  const badge = document.getElementById("bell-badge");
  const newest = Number(badge.dataset.newest);
  const last = Number(localStorage.getItem("tb-alerted") ?? newest); // first run: no backlog
  localStorage.setItem("tb-alerted", String(Math.max(last, newest)));
  if (newest <= last || Notification.permission !== "granted") return;
  if (document.visibilityState === "visible" && document.hasFocus()) return; // they can see the bell
  const res = await fetch(`/api/notifications?after=${last}`, { headers: { Accept: "application/json" } });
  if (!res.ok) return;
  const reg = await navigator.serviceWorker.ready;
  for (const n of (await res.json()).filter((n) => !n.read)) {
    reg.showNotification(n.text, { body: n.detail, tag: `n-${n.id}`, data: { url: `/?task=${n.task_id}` } });
  }
});

// Called from the "Turn on desktop alerts" button: must be a click, or browsers refuse to ask.
async function tbEnableAlerts() {
  await navigator.serviceWorker.register("/sw.js");
  const answer = await Notification.requestPermission();
  tbRenderAlertState(answer); // swaps the three states shown in 4.2
}

The tag makes the OS replace a notification instead of stacking duplicates when two tabs both react. Wording of the text is built by the server ("Asha assigned you a task" with the title and due date as the body) so the HTML list and the OS toast always agree.

4.6 Accessibility, carried over from the critique

  • The bell's accessible name includes the count ("Notifications, 2 unread"); the visual badge is aria-hidden. A polite live region announces "1 new notification" when the badge count rises.
  • Unread is shown by a dot, weight and tint, and a visually hidden "Unread." prefix, never colour alone. Chips are 12px at weight 600, matching the planned typeset fix.
  • Every action is a real button with a label, reachable by keyboard; the popover closes on Esc and returns focus to the bell. Touch targets are 44px on the phone.
  • Marking read, unread and dismissing give visible feedback by re-rendering the row; follow the "Saving / Saved" pattern chosen for the drawer so the two feel the same.

6. Phase 3: alerts when the browser is closed (optional)

Web Push lets the server wake a service worker even when no tab is open. It is the only way to reach an iPhone in someone's pocket. It comes with real costs for this project, which is why it is a separate, later decision.

NeedsDetail
A Python dependencypywebpush, which pulls in cryptography. The project currently has five runtime dependencies. This is the first addition that would be felt on the Windows PC (a compiled wheel, an update to watch).
A signing key pairA VAPID key pair, generated once by a new CLI command and kept in .env. Losing it means everyone must press "Turn on desktop alerts" again.
A tablepush_subscriptions (id, user_id, endpoint UNIQUE, p256dh, auth, created_at). One row per person per browser. Saved by POST /notifications/subscribe; removed on sign-out and when a push returns 404 or 410 (expired).
SendingAfter the transaction commits (never inside it), a function in a small push.py posts to each subscription. It must not slow down or fail the assignment: wrap it, log failures, move on. Run in a thread so the request returns immediately.
Outbound internetThe server PC must reach Google, Mozilla or Apple push services. It already has internet for Tailscale, but this is a new external dependency. If those services are down, the in-app inbox and Phase 2 still work.
PrivacyThe payload is end-to-end encrypted to the person's browser, so the push service cannot read it. Even so, keep it short: "Asha assigned you a task" plus the task id, and let the page fetch the title.

Recommendation: build Phases 1 and 2 first. They cover the main desk-based use at no dependency cost. Ask the three users whether they keep the board open all day. If the answer is "no, I close it", or if phones matter, then Phase 3 is worth its cost; if yes, it is not.

Checked against the project's own tests for a new feature

  1. Would the firm notice it missing? Yes, for the people who are assigned work they did not create. That is the point of a shared board with deadlines.
  2. Can it reuse what exists? Yes: the same polling triggers, fragments, store.py transaction, 204 + HX-Trigger pattern and JSON mirror.
  3. Does it add a dependency or background process? Phases 1 and 2: no. Phase 3: one dependency, and no long-running process.
  4. Does it keep the history complete? Yes: the thread's event row is unchanged, and notifications are explicitly not the record.
  5. Testable without the real clock or network? Yes for Phases 1 and 2 (fixed clock, SQLite). Phase 3 sending is isolated behind one function that tests replace.
  6. One obvious place? The rule lives in two lines in store.py.

8. Open questions for you

  1. Recurring tasks: should the new occurrence notify the assignees (so a clerk hears next quarter's return now exists), or stay silent because nobody assigned it?
  2. What the toast reveals: task titles contain client names. Should the OS notification show the title (more useful), or only "Asha assigned you a task" (safer on a shared or locked screen)? The in-app inbox shows the title either way.
  3. More events later: due date changed on your task, a comment on your task, a task of yours becoming overdue? Each is a new kind and a new line in the inbox; none are in this proposal.
  4. Phone placement: a bell in the top bar, or an Alerts entry next to Me in the bottom tabs?
  5. Phase 3: do the three users keep the board open all day, and does anyone want alerts on an iPhone?
  6. Sequencing with the UX critique fixes: the new bell and panel should use the new chip sizes and the "Saved" pattern, so building them after issues 1 and 3 avoids doing the styling twice.
